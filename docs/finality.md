# How accounting waits for finality

Studio currently rejects `StorageType.LATEST_FINAL` inside a contract storage read. This is visible in the [Studio host implementation](https://github.com/genlayerlabs/genlayer-studio/blob/main/backend/node/genvm/base.py#L635). A live diagnostic returned the registered agent through the default view while the explicit finalized view timed out. The first review quote also finalized with an execution timeout before producing a risk judgment. Those failures are retained in the maintainer journals. Selecting that storage flag in source is therefore not enough to establish working accounting on Studio.

Ballast uses finalized message provenance instead. The [GenLayer message lifecycle](https://docs.genlayer.com/developers/intelligent-contracts/features/messages) specifies that a child transaction is created only when its parent reaches the selected state, and then reaches consensus independently. A registry revision, policy version, court decision, filing seal or settlement emits a fixed callback to its own contract with `on='finalized'`. The callback requires the contract itself as sender and checks the exact payload against an immutable local record. No externally callable method accepts facts and forwards them to this callback. Repair methods accept an identifier and construct the payload from the contract's own records.

Only these callbacks can populate the `get_final_*` records. Consumers read those records through Studio's supported default view. The callback transaction may itself be pending, but its facts already came from a finalized parent. Reading it early can expose a true finalized fact; rolling it back can temporarily remove that fact. It cannot turn a reversible court decision into a payable verdict. This depends on the protocol honoring the documented finalized emission trigger and authenticating the sender of emitted calls. Ballast does not claim that the default storage view is finalized storage.

A source may have several versions. Immutable policy versions remain available for delayed callbacks, and monotonic pointers prevent older messages from replacing newer confirmations. The registry uses the same rule for manifest revisions. Final operator records advance only with their settlement count. A court verdict cannot be edited after finalization. Settlement recomputes the canonical claimant event, enforces the independently evidenced loss, checks policy dates and applies the remaining aggregate policy limit locally.

The server checks confirmation availability before signing a quote, claim, settlement or acknowledgment request. A pending confirmation or network outage leaves an unsigned, safely retryable operation with a clear message. Contract checks remain authoritative.

A pool settlement first confirms its accounting record. Only after that confirmation itself finalizes does it emit the court acknowledgment. An interrupted message can be republished safely. Acknowledgment never controls payment and cannot reduce exposure twice. The unresolved account index retains the case until acknowledgment succeeds.

Expiry has an additional barrier. After the filing window closes, the court seals the cumulative amount requested by every filed case. It confirms this immutable seal before asking the pool to expire cover. The pool retains the smaller of remaining cover and sealed requests less requests it has already settled. It does not infer that there are no claims from an absent or delayed message, and acknowledgment delays do not hold extra capital. No new case can be filed after sealing.

Direct tests check callback authentication, exact immutable payloads, emission triggers, missing proof refusal, delayed and repeated delivery, monotonic pointers, stale manifest and closure guards, and cumulative runoff accounting. These are application tests. The [Studio receipt record](review-finality-result.json) verifies all five actual parent and child lineages: agent, policy, court decision, pool settlement and court acknowledgment. It checks the exact parent calldata, finalized trigger, sender, target and successful finalized child execution. The separate lifecycle also checks native payment and pool accounting before a deployment is promoted.
